Let your tool find its config in .config/.

Help projects keep their root directories clear by automatically discovering your tool’s configuration in .config/. Keep your existing file format and configuration locations—just support one more place to look.

Add support to your tool ↓

Add .config/ support to your tool

  1. Choose a predictable path. Use a file such as .config/your-tool.yml, or a directory such as .config/your-tool/ when several files belong together.
  2. Preserve existing behavior. Continue supporting current locations and explicit overrides. Decide which file wins when both locations exist, and avoid silently changing the settings an existing project loads.
  3. Document discovery. Explain how you find the project root, resolve relative paths, and handle nested projects. Check these cases alongside existing configurations.

Configuration libraries

Configuration libraries can help: Cosmiconfig and c12 support project-local .config/ lookup. Check your loader’s search settings; tools can override the defaults.

Questions & rationale

Why put tool configuration in one directory?

A project can use many tools, each with its own configuration file. Keeping those files together leaves the project root easier to scan for source code, documentation and other project files. Automatic discovery lets users organize their settings without adding custom paths to every command, editor and CI integration.

Do we need another standard or tool?

The proposal is a shared directory convention. Each tool keeps its own configuration format and implements its own lookup; users do not need another tool to manage it. The name is inspired by XDG’s user configuration directory, but project-level .config/ is not part of the XDG specification.

What if configuration exists in both locations?

There is no single precedence rule across tools. A tool may select one file, merge settings in a documented order, or report a conflict. Preserve existing behavior and explicit overrides, and explain which settings take effect. See the discussion about conflicting files.

How is this different from ~/.config/?

~/.config/ holds settings for a user account. A project’s .config/ holds settings shared with everyone working on that project and can be committed to version control. Each tool decides how project settings interact with user defaults.

Why .config/ instead of config/?

The name borrows a familiar convention for tool settings and leaves an existing application or framework’s config/ directory in place. Some projects will have both; the distinction is tool settings versus application configuration. The leading dot does not make a file private or exclude it from version control. This is a convention with tradeoffs, explored in the directory naming discussion.

How should files be named inside .config/?

Use a recognizable tool name. A single file such as .config/tool.toml keeps the layout simple; a directory such as .config/tool/ groups related files and can match a tool’s user-level layout. Existing tools use both patterns, including some filenames with a leading dot. Document the paths your tool accepts. The naming discussion remains open.

Do XDG environment variables change the project path?

No. This convention uses .config/ within the project, independent of an individual user’s XDG settings. If your tool also loads user or system configuration through XDG, respect XDG_CONFIG_HOME and XDG_CONFIG_DIRS for those locations. Keep that lookup separate from project discovery. See the XDG discussion.

Should every file move out of the project root?

This proposal is for tool settings. Keep manifests, lockfiles and files such as .gitignore and .editorconfig in their expected locations. Move a tool’s configuration only when it supports that location. Caches, temporary files and secrets need their own appropriate storage.
